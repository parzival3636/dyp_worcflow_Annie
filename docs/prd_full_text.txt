0. How to read this document
This is the single source of truth for the team and for any AI coding agent working in the repo. Table names, status values,
endpoint paths and JSON field names are exact: do not rename them. If something is unclear, pick the simplest option
that satisfies the acceptance checklist (section 20) and note the decision in `/docs/decisions.md`. Working title: Pilot.
1. Summary
Pilot is a Telegram bot + GitHub integration + Jira-style web app that runs a college group project. A lead describes the
project in Telegram. Pilot creates the GitHub repo, invites teammates, generates detailed tasks, bundles dependent tasks
into independent blocks, and assigns blocks evenly. Then it runs a follow-up loop: it asks owners for updates on Telegram,
interprets messy replies, and updates task status. When someone says done, Pilot checks their real commits on GitHub
and returns a verdict with confidence. A Guide agent oversees everything: it knows who contributed what and when,
catches contradictions between teammates, routes blockers to the person who can fix them, and shows the ripple effect of
delays.
Pitch line: Other bots collect status updates. Ours checks them.

4. Scope
In scope: Telegram bot, GitHub repo creation and collaborator invites, LLM task generation, dependency bundling, equal
assignment, Jira-style web board, scheduled check-ins, reply interpretation, GitHub verification, contradiction detection,
blocker routing, ripple effect, contribution ledger and charts, Guide Q&A and reports.
Out of scope: agile or sprint framework generation, native mobile app, browser extension, GitHub webhooks (we poll),
user accounts and login (identity comes from Telegram; web app selects a project by code).

Statuses: todo, in_progress, blocked, claimed_done, needs_review, verified_done.
●
todo →in_progress: first progress reply, or first matching commit.
●
in_progress ↔blocked: blocker reply opens a blocker; resolving it returns the task to in_progress.
●
any open status →claimed_done: member claims completion.
●
claimed_done →verified_done: verifier verdict is verified with confidence ≥0.7.
●
claimed_done →needs_review: verdict is partial, or no_evidence, or confidence below 0.7.
●
needs_review →claimed_done: member reports more work or a new matching commit appears (re-verify).
●
needs_review →verified_done: lead override (button in web app).
●
verified_done →in_progress: lead reopens.
The bot never sets verified_done from a chat reply alone. Only the verifier or a lead override can.
10. End-to-end workflow, A to Z
Step 1. Pre-event setup. Create the bot with @BotFather and save the token. Create a GitHub personal access token
(repo scope) for the account that will own demo repos. Fill .env. Start backend, bot and frontend. All four builders confirm
they can message the bot.
Step 2. Project creation (Telegram). The lead sends `/newproject <idea text>`. The backend calls the LLM (P1) to
produce name, one-paragraph summary, and duration in hours (default 20 if missing). It inserts a project with a short code,
creates the lead as a member (role lead), and calls GitHub to create repo `pilot-<slug>-<code>` with a README and a
CONTRIBUTING.md stating the commit rule: every commit message must contain its task key, like [T-4]. The bot
replies with the repo URL, the project code, and a join link `https://t.me/<bot>?start=join_<code>`.
Step 3. Members join. Each member opens the join link. The bot receives `/start join_<code>`, records telegram_id and
name, and asks for a GitHub username. The backend validates it (GET /users/{login}), sends a collaborator invite (PUT
/repos/{owner}/{repo}/collaborators/{login}), stores github_login, and tells the member to accept the invitation on GitHub.
The poller marks invite_status = accepted when the user appears in the collaborators list. Event: member_joined.
Step 4. Task generation. The lead sends `/plan` (or clicks Generate Tasks in the web app). The LLM (P2) receives the
idea, team size, skills list and duration, and returns 12 to 20 detailed tasks with description, 2 to 4 acceptance criteria,
effort 1 to 8, dependencies by title, and milestone flags (including a final Demo milestone). The planner validates the
result: unique titles, dependency titles exist, cycles removed (drop the offending edge), at least one milestone. Keys T-
1..T-n are assigned. Events: task_created.
Step 5. Human edit on the web app. The lead opens the Tasks page: edit any field, add a task, delete a task, edit
dependencies. Delete removes the task and its edges. All edits write task_updated events.
Step 6. Bundling. The lead clicks Bundle & Assign. The planner builds a graph of non-milestone tasks with hard
dependency edges and computes connected components (section 11, F5). Each component becomes one block:
dependent tasks are bundled into a single independent unit of work. Milestone tasks are excluded from bundling and
depend on blocks.
Step 7. Equal assignment. The planner assigns blocks to members with greedy load balancing (F6). Oversize blocks are
flagged. The lead sees a preview (blocks, owners, loads) and confirms. Events: tasks_bundled, block_assigned.
Step 8. Deadlines and kickoff. Deadlines are computed from the project window and dependency order (F4). The lead
sends `/kickoff` or clicks Start Project. Every member receives a Telegram message listing their block, each task with
deadline and acceptance criteria, and the commit rule. The scheduler is armed.
Step 9. Core loop: check-in. Every 60 seconds the scheduler selects tasks needing a check-in (F8 rules) and sends the
owner a Telegram message asking for a specific update on a specific task. Event: checkin_sent. Message stored with
direction = out.
Step 10. Core loop: reply interpretation. Any incoming Telegram text goes to the reply handler. It determines which
task the reply is about, sends the reply plus context to the LLM (P3), and gets structured JSON: intent, new status,
blocker, progress, evidence links, claims about others, clarification need. Low confidence or unclear replies trigger one
clarifying question instead of a status change.
Step 11. Status update and side effects. The handler applies the transition (section 9), writes events, and then runs
side effects in order: (a) if a blocker is present, open it and run blocker routing (F12); (b) run contradiction check (F11); (c)
recompute ripple risk for downstream tasks (F13); (d) if the intent is completion, go to step 12.
Step 12. Completion claim triggers GitHub verification. Status becomes claimed_done. The verifier (F9) gathers the
member's commits and PRs since the task started, summarizes diffs, and asks the LLM (P4) to judge them against the
acceptance criteria.

Step 13. Verdict handling. Verified (≥0.7): verified_done, member congratulated, completed_at set, downstream tasks
recalculated. Partial or no_evidence: needs_review, the bot tells the member exactly what is missing (for example
criterion 2 has no matching code, or no commits with [T-4] found) and invites them to push and reply again. The web
board shows both the claim and the verdict.
Step 14. Guide oversight. Every 5 minutes the Guide scans the project: overdue tasks, stale in_progress tasks with no
commits, blocked tasks with no routing, unresolved contradictions. It takes actions (nudge, escalate, route) and writes
guide_note events. It also answers questions from Telegram `/ask` and the web chat panel.
Step 15. Live visualization. The web app polls the snapshot endpoint and updates board, graph, activity log, and
contribution chart without refresh.
Step 16. Wrap-up. `/report` or the Report button makes the Guide produce a final summary: who contributed what
(commits, lines, tasks verified), what was completed and when, claimed versus verified counts, blockers and how long
they lasted, and unresolved risks.
11. Features and how to implement each
F1. Telegram pipeline (owner A)
Handlers: `/newproject`, `/start join_<code>`, `/plan`, `/kickoff`, `/mytasks`, `/status`, `/ask <question>`, `/report`, `/help`,
and a catch-all text handler for replies. Identity: look up member by telegram_id. Free text from a member goes to the
reply handler (F8). Keep per-member conversation state in memory and DB: active_task_id (last task asked about) and
awaiting_clarification flag. Always write inbound and outbound text to message. Wrap every handler in try/except and
reply with a friendly error so the demo never goes silent.
F2. GitHub pipeline (owner B)
Functions in gh.py: create_repo(name), add_collaborator(repo, login), list_collaborators(repo), list_commits(repo, since),
get_commit(repo, sha) (files, additions, deletions, patch), list_prs(repo). Poller (every 45 seconds): fetch commits since
project.last_polled_at, upsert into commit_log, map author_login to member_id, extract task key with a regex for \[T-
\<number>\] (else leave task_id null and let the verifier match semantically), write commit_seen events, move todo →
in_progress for the matching task. Cache everything; GitHub rate limit is 5000 requests per hour with a token, which is
plenty at this volume.
F3. LLM layer (owner C)
call_json(system, user, model_cls, retries=2): temperature 0.1, instruct JSON-only output, strip code fences, validate with
Pydantic, on failure retry with the validation error appended. Log every prompt and response to /docs/demo-
evidence/llm.log. Fallback: if all retries fail, return a safe default (intent unclear, ask a clarifying question). Keep model
name in config so it can be swapped.
F4. Task generation and deadlines (owner C)
LLM P2 produces tasks. Deadlines: take the project window [starts_at, ends_at], reserve the last 10 percent for the final
milestone, and for each block distribute its tasks in topological order, each task's duration proportional to its effort, so a
task's deadline is block_start + cumulative_effort / block_total_effort * block_window. Milestone deadline equals ends_at.
In demo mode, a config switch compresses deadlines into minutes so check-ins fire live.
F5. Bundling dependent tasks into independent blocks (owner C)
def bundle(tasks, deps):
# non-milestone tasks, hard deps only
parent = {t.id: t.id for t in tasks}
def find(x):
while parent[x] != x:
parent[x] = parent[parent[x]]; x = parent[x]
return x
for a, b in deps:
parent[find(a)] = find(b)
blocks = {}
for t in tasks:
blocks.setdefault(find(t.id), []).append(t)
return list(blocks.values())
# each list is one independent
block
Block weight is the sum of task effort. Each task row gets block_id. A block can be worked end to end by one person
without waiting on anyone else.

See section 15. Key behavior: board columns follow the status machine, cards show owner color, deadline, risk badge,

F8. Core loop: check-ins and replies (owner A)
Check-in selection (scheduler every 60 seconds) for tasks with status in todo, in_progress, blocked and project status
running:
●
Kickoff message once at start.
●
Cadence: every CHECKIN_HOURS (default 4) since last_checkin_at.
●
Extra pings at deadline minus 24h, deadline minus 2h, and when overdue.
●
Cooldown: at most one check-in per member per 30 minutes (bundle several tasks into one message); quiet
hours 22:00 to 08:00 skipped.
●
Escalation: after 2 unanswered check-ins, notify the lead via the Guide.
●
Demo override: the Run follow-up now button and the `/followup` command ignore cadence and cooldown.
Check-in text is generated by the LLM or a template with task title, deadline, and a gentle question, plus inline buttons: In
progress, Blocked, Done. Buttons are a convenience; free text must work equally well.
Reply routing: if active_task_id exists and the reply is plausibly about it, use it; otherwise pass all of the member's open
tasks to the LLM and let it pick task_key. Replies about several tasks in one message are allowed.
Handling matrix:
●
progress_update →set in_progress, store progress percent.
●
blocker →open blocker, set blocked.
●
completion_claim →claimed_done, trigger verification.
●
question →answer from task data or hand to the Guide.
●
off_topic or unclear →one clarifying question, no status change.
●
Silence →covered by escalation above.
F9. GitHub verification (owner B)
1.
Deterministic pre-check: if the member has zero commits since task.started_at (or task creation), return
no_evidence without calling the LLM.
2.
Collect candidate commits: those with the [T-key] first, then the member's other commits in the window. Fetch
files, additions, deletions, and truncated patches (cap 6000 characters total).
3.
Call P4 with title, description, acceptance criteria, and commit summaries.
4.
Return {verdict, confidence, matched_shas, criteria_results[{criterion, met, note}], reason}; store in verification.
5.
Rules: verified and confidence ≥0.7 →verified_done. Otherwise needs_review. If the matching commits were
authored by someone else, say so and credit them in the ledger.
6.
Re-verification triggers when a new commit with the task key arrives while the task is needs_review, or when the
member replies done again.
The UI always shows confidence and reason, never a bare pass or fail.
F10. Guide agent (owner C)
A tool-calling loop (max 6 steps per run). Read tools: get_project_snapshot(), get_task(key),
get_member_contributions(member), get_commits(task_or_member), get_timeline(until), get_open_blockers(), get_risks().
Action tools: message_member(member, text), flag_contradiction(...), route_blocker(blocker_id), propose_split(block_id),
post_note(text). If the model has no native tool calling, use a JSON action loop: the model returns a tool name and args,
the backend executes and feeds back the result, until the model returns a final text.

Modes: (1) Proactive tick every 5 minutes with a checklist prompt (overdue, stale, unrouted blockers, open

F11. Contradiction detection (owner C)
Two layers.
●
Rules (cheap, run on every status change): (1) member says a dependency or another person's work is done,
while that task is not verified_done or its owner reported blocked; (2) two members describe the same shared
item with opposite status; (3) claimed_done contradicted by verification no_evidence.
●
LLM (P5): feed the latest messages and statuses of related tasks (same block, handoff neighbors, milestone
predecessors) and ask for conflicts.
On detection: insert contradiction, message both people with the specific conflict and one question each (for example:
Meera said the integration is done, Kabir said he is waiting on the API. Which is accurate?), and mark resolved when
replies agree or GitHub evidence settles it. Show open contradictions as a red banner on the board.
F12. Blocker routing (owner C with A)
When a reply yields a blocker with description, type and needed_from, the Guide picks who can unblock it. Candidate
order: (1) owner of the task named in needed_from or the upstream task; (2) member whose skills match; (3) the lead.
Call P6 with the member list, owners, and skills to choose one with a reason. Message the candidate: Kabir is blocked on
test credentials for T-7. Can you help? with buttons I can help and Not me. Set blocker.status = routed. If no answer in 2
hours (demo: 2 minutes) move to the next candidate and finally notify the lead. When the helper confirms or the blocked
member says it is resolved, set blocker resolved, notify the owner, return the task to in_progress. Log every hop as an
event.
F13. Ripple effect (owner C data, D visuals)
Tasks form a DAG with hard edges, handoff edges, and milestone edges. For each task compute slip, how far its
projected finish is behind its deadline: for a blocked or overdue task, slip = now - deadline (or time since blocked,
whichever is larger); for downstream tasks, propagate slip along edges. A downstream task has slack = deadline -
upstream_deadline - effort_hours. Risk: critical if slip > slack and the task is within 12 hours of its deadline or already late;
at_risk if slip > 0.5 × slack; else ok. Milestone risk is the worst risk among its predecessors. Store task.risk; write
risk_changed events. Frontend shows the graph with edges from the blocked node glowing red and a text line: Kabir is
blocked, so the Demo milestone is at risk.
F14. Contribution visuals (owner D)
Series per member from commit_log (cumulative commits or lines per hour, one color per member) in a Recharts line
chart, plus a table: member, commits, lines, tasks verified, last active. The same colors identify owners everywhere (board,
graph nodes, chart).

16. LLM prompts (P1–P6)
All prompts force pure JSON. `call_json` strips fences and validates against a Pydantic model. Temperature 0.1. Two
retries with the validation error appended.
P1 – Project parse (`/newproject`)
System: “You extract a short project name, one-paragraph summary, and estimated duration in hours from a free-text idea.
Reply only with JSON.”
User: the idea text.
Output schema: `{ "name": str, "summary": str, "duration_hours": int }`
P2 – Task generation (`/plan`)
System: “You are a project planner for a college hackathon team. Produce 12–20 concrete engineering tasks. Each task
needs title, description, 2–4 acceptance criteria, effort 1–8, dependencies (list of other titles), and is_milestone flag.
Include a final Demo milestone. No cycles. Reply only with JSON.”
User: idea + team size + skills + duration.
Output schema: `{ "tasks": [ { "title", "description", "acceptance_criteria": [str], "effort": int, "depends_on": [str],
"is_milestone": bool } ] }`
P3 – Reply interpretation (core loop)
System: “You interpret a team member’s free-text reply about their work. Decide intent, which task, new status,
progress %, blocker details, claims about other people, and whether clarification is needed. Reply only with JSON.”
User: member’s open tasks + recent messages + the new reply.
Output schema: `{ "task_key": str|null, "intent":
"progress_update"|"blocker"|"completion_claim"|"question"|"off_topic"|"unclear", "new_status": str|null, "progress": int|null,
"blocker": { "description", "type", "needed_from" }|null, "claims_about_others": [str], "needs_clarification": bool,
"clarifying_question": str|null, "confidence": float }`
P4 – Verification (F9)
System: “You judge whether the supplied commits and patches satisfy the acceptance criteria of a task. Be strict. Reply
only with JSON.”
User: task title + description + criteria + list of commit summaries (sha, message, files, truncated patch).
Output schema: `{ "verdict": "verified"|"partial"|"no_evidence", "confidence": float, "matched_shas": [str], "criteria_results":
[ { "criterion": str, "met": bool, "note": str } ], "reason": str }`

17. Error handling & resilience
●
Every Telegram handler is wrapped in try/except; on failure the bot replies “Something went wrong, try again in a
moment” and logs the traceback.
●
LLM calls: 2 retries with validation error; final fallback is “unclear →ask clarifying question”.
●
GitHub rate-limit or network errors: the poller skips the cycle and retries next interval; never crashes the process.
●
SQLite: single writer (the Python process); no concurrent write risk.
●
If repo creation fails, the bot still creates the project and tells the lead the GitHub step failed so they can paste a
pre-made repo URL.
●
All state changes are transactional (event + entity update in one commit).
